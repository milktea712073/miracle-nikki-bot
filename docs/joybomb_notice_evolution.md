# JoyBomb／Facebook 公告寫作與結構演變

> 本文件是唯讀研究報告。分析資料來自 JoyBomb Wayback 公告頁與目前本機唯讀 Facebook 原始公告樣本；不使用現有 Parser 的判斷、不修改任何程式、Schema、資料庫或既有研究報告。

## 先看資料，而不是預設趨勢

| 指標 | 2017–2019 | 2020–2023 | 2026 Facebook 比較樣本 |
|---|---:|---:|---:|
| 分析公告數 | 20 | 20 | 20 |
| `h1` 為「新聞公告」 | 12 | 0 | 不適用 |
| 頁首另有 `h3`「活動」分類 | 10 | 0 | 不適用 |
| 可直接辨識「活動一／二…」段首的頁面 | 14 | 15 | 2 |
| 可辨識的編號活動段總數 | 61 | 54 | 2 個顯式「活動一」；多數以單篇主題呈現 |
| 有明示「活動時間」 | 頁內常見，但未作逐欄量化 | 頁內常見，但未作逐欄量化 | 20 |
| 有明示「活動內容」 | 模板常以「活動方式／內容」呈現 | 模板常以「活動內容」呈現 | 18 |

這些數字支持兩個結論：

1. **舊版與中期都不能假定一篇公告只有一個活動。** 中期仍有大量多段頁面，並非單向地變成「一篇只講一件事」。
2. **近期 Facebook 的單一貼文更常圍繞一個主題或一個活動單元。** 但其文內仍可能有「活動一」、加購、登入送或復刻資訊，因此不應把「較少編號段」誤解為永遠單一 event。

## 第一階段：2017–2019 舊版 JoyBomb

### 公告結構

早期模板最明顯的特徵是泛用頁首：多數頁面呈現 `h1：新聞公告`、`h3：活動`、`h4：日期`。真正的資訊在正文段落。

- Notice 9897 使用「活動一、古典音樂會」「活動二、同場加映－韓國櫻花戀曲」「活動三、公主級加倍活動」。
- Notice 9938 同頁放入登入、端午活動、大喵任務、關卡加倍與累計花費。
- Notice 11138 同頁混合冰雪舞會、累計儲值、限定販售與關卡加倍。
- Notice 11403 的標題雖是「廢墟天使與貓咪共進茶會」，正文卻另列登入送、小屋限時閣與套裝活動。

因此這一階段大量使用「活動一」「活動二」或「【活動一】」作為可讀的分段符號，並頻繁把登入送、商城、儲值、加倍與活動本體放進同一頁。切段可行，但切出來的內容不都應建立 Knowledge DB event。

### 標題與命名

- `新聞公告`：只能作為頁面主標題／來源標題，完全不適合作為 event.name。
- `活動`：只是一級分類，適合作為 source section 或 content type 提示。
- 「活動一、古典音樂會」：是最強的 event.name 候選，因為同段有期間、玩法與套裝資訊。
- 「十二月劇團」：在古典音樂會的正文中是演出團體、世界觀或宣傳主題；除非能跨檔期證明其固定對應同一玩法與套裝組合，否則不應直接作 event identity。

### Parser 難度：高

| 工作 | 評估 | 原因 |
|---|---|---|
| 切段 | 中 | 有大量明確編號，但仍存在未編號的敘事與補充段。 |
| 抽活動名稱 | 高 | 頁首多為「新聞公告」，需由正文段首找名稱；同段可能還有套裝、道具與宣傳名稱。 |
| 抽套裝 | 中高 | 套裝常與道具、禮盒、部件一起出現，需限制在已選定區塊。 |
| 判斷 event | 高 | 一頁通常包含主活動、儲值、登入送與加倍；不能把所有段落視為同一 event。 |

## 第二階段：2020–2023 中期 JoyBomb

### 公告結構

中期的 `h1` 多改為具體、行銷式標題，例如「蔚藍深海 奇幻冒險」、「虛擬幻域 時空之旅」、「寒夜森森 幽林餘燼」。這比「新聞公告」更有資訊量，但正文的多段結構沒有消失。

- Notice 13388：深海奇遇、累計購買鑽石贈套裝、登入送、公主級雙倍。
- Notice 13389：復刻螢光之靈、大喵任務、禮盒、神秘商店、公主級雙倍。
- Notice 13895：時幻之域與多種禮盒、累計儲值、長期登入送。
- Notice 14904：奇妙偵探社－醉月樓珍饈之宴、大喵任務、聯邦商貿禮盒。
- Notice 16793：幽林餘燼、幽夜商店禮盒、單筆儲值贈套裝、時光回溯、公主級雙倍。

這個階段的主標題較常指向主題活動，但仍可能在同頁塞入數個不同內容類型。特別是故事套裝、螢光之靈、儲值禮盒與回歸內容，名稱互相接近，不能只以標題或首個套裝做合併。

### 標題與命名

- 主標題：可作較強的 source title，也可作「主活動」弱候選。
- 正文「活動一、時幻之域」「活動一、幽林餘燼」：仍是較可靠的 event.name 候選。
- 「奇妙偵探社」「螢光之靈」「時光回溯」：通常是玩法／長期系統／回歸機制，較像 event family 或 acquisition context；必須搭配本次主題、時間與套裝組合才能得到具體 event。

### Parser 難度：中高

| 工作 | 評估 | 原因 |
|---|---|---|
| 切段 | 中 | 20 篇中 15 篇仍有可辨識編號段，但另有新聞稿式頁面需讀自然段落。 |
| 抽活動名稱 | 中 | 主標題已較具體，正文段首可交叉驗證；仍要避免把商店／禮盒名稱當主活動。 |
| 抽套裝 | 中 | 套裝名稱更常以「贈套裝」「故事套裝」描述，但儲值禮盒與部件仍容易造成誤判。 |
| 判斷 event | 中高 | 主活動通常較清楚，然而同頁附屬的回歸、商店、登入與雙倍仍需拆開分類。 |

## 第三階段：2024–2026 近期風格（以 2026 Facebook 為實證）

### 資料限制

JoyBomb Wayback 可見的最後 capture 位於 2024 年初，且目前本機唯讀 Facebook 樣本僅有 2026。故本節不將 2026 的觀察回推為 2024 或 2025 的確定事實；它只說明目前官方 Facebook 公告的近期結構。

### 公告結構

近期 Facebook 貼文常在開頭用明確標籤與固定欄位：

```text
【預告】活動名稱／玩法
✨ 活動時間：…
✨ 活動內容：…
```

20 篇樣本全部有「活動時間」，18 篇有「活動內容」。例如：

- 「【預告】童心起航 藍空趣旅」在開頭直接給活動時間、主題與套裝【藍空趣旅】。
- 「【復刻】願之庭 仲夏夜之夢」清楚分出玩法 family「願之庭」、本次主題「仲夏夜之夢」與復刻狀態。
- 「【復刻】聚合雙子之力 回溯往日繁星」清楚標出滿天繁星玩法與本期復刻套裝組合。
- 「【福利】畢業季 登入送」以分類標籤、期間與固定贈禮構成單一福利公告。

近期仍存在一篇內多單元的例外，例如「奇淵之嶼 心願饋贈」使用「活動一、奇淵之嶼」，並可能將儲值與套裝檔位放在同一篇；這類貼文不應因排版較新而跳過切段。

### 標題與命名

| Facebook 元素 | 最適合用途 |
|---|---|
| `【預告】`、`【復刻】`、`【福利】` | content intent／period type 的輔助訊號；不是 event.name。 |
| 開頭主題名，例如「童心起航 藍空趣旅」 | source title 與 event.name 強候選。 |
| `✨ 活動時間`、`✨ 活動內容` | 活動邊界與時間解析的高價值結構訊號。 |
| 「願之庭」「滿天繁星」「凝砂」等 | event family／玩法分類候選。 |
| 方括號內套裝 | event_suit 候選；不可單獨決定 event identity。 |

### Parser 難度：中

| 工作 | 評估 | 原因 |
|---|---|---|
| 切段 | 低到中 | 多數貼文是一個主題單元，且有固定時間／內容標籤；少數「活動一」或複合公告仍須切段。 |
| 抽活動名稱 | 中低 | 開頭標籤與主題通常可用，仍需排除純海報、桌布、得獎名單與社群活動。 |
| 抽套裝 | 中 | 明確「套裝【名稱】」增加可靠性，但同文仍會列部件、代幣與獎勵。 |
| 判斷 event | 中 | 主題邊界較清楚；復刻、family 與附屬儲值仍需與具體活動名分離。 |

## 是否存在年代專用 Parser？

### 不應做成三套彼此分離的 Parser

三個時段的共同點仍很強：公告都可能包含主題名稱、時間、玩法、套裝、儲值與福利；套裝和活動名稱也都可能以括號、引號或宣傳句出現。完全分叉會造成規則重複、行為漂移與難以驗證。

### 應共用核心 Parser，加上來源／年代前處理

建議採用一套共用的活動、時間、套裝與復刻解析核心，前端增加來源提示與 section splitter：

| 來源／年代條件 | 額外策略 |
|---|---|
| 2017–2019 JoyBomb | 優先識別 `活動一、`、`【活動一】`；不要使用 `h1：新聞公告` 當活動名。 |
| 2020–2023 JoyBomb | 保留相同切段；把具體 `h1` 作 source title／主題弱候選，仍以段首和同段時間驗證。 |
| 近期 Facebook | 優先利用開頭分類標籤、`活動時間`、`活動內容`；無切段證據時以整篇作單一主題單元。 |

## 各年代皆成立的規律

1. **公告標題不是永久 event identity。** 標題可能泛用、宣傳化，或同時涵蓋多個活動。
2. **活動名稱必須與同一內容區塊的時間、玩法或套裝組合交叉驗證。**
3. **玩法 family 與具體 event 必須分開。** 願之庭、螢光之靈、滿天繁星、奇妙偵探社等不能直接把所有檔期合併。
4. **登入送、商城禮盒、雙倍與維護資訊不因同頁出現就屬於主 event。**
5. **套裝名稱只能是輔助證據。** 它可用來描述 event composition，不能單獨決定 event 是否相同。

## 只屬於舊版 JoyBomb 的規律

- `h1：新聞公告` 與 `h3：活動` 的固定頁面框架。
- 大量以「活動一／二／三」在同一 HTML 頁串接多個內容單元。
- 同頁把活動、登入、儲值、商店與關卡加倍完整打包的比例明顯較高。
- 早期短標題與宣傳敘事的分離更強，必須從正文取得具體名稱。

## 建議的資料流程

```text
Raw document
  ↓
Source-aware normalization
  - JoyBomb legacy: 讀取頁首、段首與段落順序
  - Facebook: 保留開頭標籤、時間／內容標記與換行
  ↓
Section splitter
  - 高信心：活動一／二、【活動一】
  - 次要：時間／內容標籤、獨立短標題
  ↓
Section classifier
  - event / suit_event / welfare / recharge / maintenance / other
  ↓
Shared parser
  - event name candidate
  - event family candidate
  - period, time, suit candidates
  ↓
Knowledge candidate / needs_review
```

### 最保守的落地原則

- 有明確段首、期間與玩法／套裝組合：可產生 event candidate。
- 有段首但只有禮盒、加倍、登入或資源：先分類為附屬內容，不強建 event。
- 無段首、名稱互相競爭、或一段混合社群／系統與遊戲內容：保留 `needs_review`。
- 一個 raw document 必須能產生多個 section；因此也應允許它產生多個 parse draft。來源貼文 ID 是 provenance，不能取代 section identity。

## 最終判斷

需要的是**少量來源／年代前處理規則**，不是三套獨立 Parser。舊版 JoyBomb 的首要問題是切段與泛用頁首；中期是具體主標題與多段附屬內容並存；近期 Facebook 則提供較清楚的標籤、時間與內容欄位。共用核心 Parser，加上「Raw → Section → Parser → Knowledge」分層，能同時保留跨年代一致性並避免把舊公告的多活動內容硬合併成一個 event。
