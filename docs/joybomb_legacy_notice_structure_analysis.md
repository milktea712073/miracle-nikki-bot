# JoyBomb 舊版公告：活動命名與正文結構分析

> 範圍：唯讀檢視 JoyBomb Wayback 樣本及 21 篇個別 archived HTML。本報告不使用現有 Parser 推論、不讀寫 SQLite，亦不改動任何既有程式或研究報告。

## 結論摘要

1. 舊版頁面的 `h1` 常是「新聞公告」，`h3` 常是「活動」；兩者是**頁面／公告分類**，不是可直接作為活動名稱的欄位。
2. 2017–2018 常見「活動一、…」「【活動一】…」等正文段首；2019 以後仍常見同一結構，但新聞稿式頁面也可能用段落標題或自然語句列出多個活動。
3. 同一公告確實經常混合主活動、登入送、儲值禮盒、關卡加倍、商店販售與系統福利。因此「一篇公告 = 一個 event」不成立；但「一個段首 = 一個正式活動」也不成立。
4. 對舊資料，最安全的順序是：**先依正文切段，再對每段判斷內容類型與名稱候選**。無法確定的段落應保留為福利／其他或 `needs_review`，不能因同頁出現套裝或儲值就硬建 event。

## 頁面標題層級的意義

### 頁面頂部「活動」不是活動名稱

在 Notice ID 9897、9938、9978、11138、11178 的舊模板中，頁首依序為：

```text
h1：新聞公告
h3：活動
h4：公告日期
```

其中「活動」只說明此頁屬於活動分類；「新聞公告」是泛用頁面主標題。兩者都不能取代正文內的「活動一、古典音樂會」等具體段首。

2018 後部分模板只剩一個較長的 `h1`，例如「蔚藍深海 奇幻冒險」或「寒夜森森 幽林餘燼」。這種 `h1` 可作**來源公告標題**與弱候選，但若正文列出多個區塊，仍不能假定 h1 只代表其中一個 event。

### 名稱欄位的保守定位

| 來源文字 | 最適合用途 | 不適合用途 |
|---|---|---|
| 頁面 `h1`／公告主標題 | `source_title`、搜尋／展示、弱名稱候選 | 自動作為永久 event identity |
| 頁面頂部分類「活動」 | `source_section`／content type 提示 | event.name、event family |
| 正文「活動一、名稱」段首 | event.name 候選、切段錨點 | 未經內容檢查就直接建正式 event |
| 「願之庭／奇妙偵探社／螢光之靈」等玩法字眼 | event family／玩法分類候選 | 將同一玩法的所有檔期合併成一個 event |
| 套裝名稱 | event_suit 候選、輔助判斷同檔期組合 | 單獨作為 event identity |

## 「十二月劇團甦醒－古典音樂會」的判斷

以 Notice ID 9897 為例，頁面 `h1` 是「新聞公告」，頂部分類是「活動」，正文先以敘事提到「十二月劇團」再列出：

```text
活動一、古典音樂會
```

「十二月劇團」在該頁的用途較接近世界觀／宣傳主體與演出團體；能直接對應期間、玩法、兌換與套裝組合的名稱是「古典音樂會」。因此：

- `古典音樂會`：較強的具體 `event.name` 候選。
- `十二月劇團` 或「十二月劇團甦醒」：保留為宣傳文字或可能的故事／系列標籤；除非跨公告反覆以完全相同名稱指涉同一玩法與套裝組合，否則不應自動當 event identity。
- `單簧管協奏曲、黑白交響樂、天空隨想曲`：套裝候選，應關聯到「古典音樂會」，而不是取代活動名稱。

## 可自動化的切段規則

### 高信心切段錨點

下列字串位於段落開頭，且後方通常接活動時間／內容時，可作為分段邊界：

```text
活動一、名稱
活動二、名稱
【活動一】名稱
【活動二】名稱
```

可接受全形／半形標點、阿拉伯數字或中文數字。切段後，時間、取得方式、套裝、儲值或登入關鍵字只能在同一段內解讀。

### 可作為次要切段提示，但不能單獨保證

- `活動時間：`、`活動內容：`、`活動方式：`
- `登入送`、`累計儲值`、`單筆儲值`、`限時禮盒`、`限定販售`
- `公主級雙倍`、`金幣／星光幣加倍`、`神秘商店`
- 新聞稿中的獨立短標題，例如「奇幻指環 即將展開」與「向陽之旅 免費套裝登場」

次要提示只可協助辨識相鄰段落。沒有段首、時間或取得方式的自然語句，不應自動切成正式 event。

## 應建立 event、僅保留內容，或 needs_review 的界線

| 情況 | 建議 |
|---|---|
| 段首具體活動名稱 + 獨立時間 + 玩法或取得方式 | 建立 event 候選；可建立一個 parse draft section。 |
| 段首是登入送、體力包、雙倍、商店禮盒 | 保留為同公告內容區塊；除非有明確可辨識活動／套裝組合，預設 welfare／recharge，不硬建套裝 event。 |
| 段首明示「復刻／復開／回歸」且名稱、玩法、套裝組合可辨識 | 建立或比對具體 event 的 period 候選；不要只因有「復刻」字眼就合併。 |
| 只有「新聞公告」但正文出現「活動一、名稱」 | 忽略泛用頁面標題，以正文段首建立候選。 |
| 維護、開機、異常修復、機率／規則說明 | 不建立 event；保留來源與內容類型。 |
| 公益合作、社群抽獎、宣傳貼文，無遊戲內玩法／時間／套裝組合 | `needs_review` 或 other。 |
| 新聞稿未編號、但明確列出兩個以上不同名稱、時間或玩法 | 允許切出多個候選段落；低信心者 `needs_review`。 |

## 對舊資料 Parser 的保守建議

1. **先做公告切段。** 舊 JoyBomb 單篇公告混合內容的比例高；在全文上直接找套裝或活動名稱，會把禮盒、加倍與主活動混為同一 event。
2. **允許一個 raw post 產生多個 parse draft。** draft 的來源鍵應能記錄 `source_raw_post_id + block_index` 或等價 section key；來源貼文 ID 只能表達出處，不能代表唯一活動。
3. **舊版與 Facebook／Fearless 可共用後段 Parser。** 可共用活動時間、套裝、復刻與玩法解析；但 JoyBomb 前面需增加來源提示與切段層，將各段送入既有規則，而不是把舊頁模板硬塞進同一全文入口。
4. **不要以頁面標題作永久 identity。** 特別是「新聞公告」、節慶宣傳文案、長新聞稿與包含多個活動的標題。
5. **需要 `needs_review` 的情況：** 無清楚段首且多個名稱互相競爭、跨段共享時間、只有獎勵／禮盒資訊、或活動與公益／系統內容混在同段。

## 最終建議

舊 JoyBomb 資料適合採用「**公告 → 區塊 → 活動候選**」的匯入前模型：

```text
Wayback notice
  ├─ block 1: 主活動（可能建立 event）
  ├─ block 2: 儲值／禮盒（通常獨立內容，不自動視為主 event）
  ├─ block 3: 登入送／加倍（welfare）
  └─ block n: 維護／系統／宣傳（非 event 或 needs_review）
```

這種分層符合玩家認知，也能避免把「同頁同檔期」誤當成「同一活動」。對正式匯入而言，寧可保留來源區塊等待校正，也不要由一篇公告或一個泛用標題自動合併多個 event。
