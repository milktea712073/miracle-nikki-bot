# JoyBomb Historical Notices and Event Identity Research

> Evidence source: JoyBomb Wayback notice text only. This report does not use the project Parser, SQLite, existing event identity, or Queue.

## Method and limits

- At most 20 notices were sampled for each Wayback capture year: 2017-2022 have 20 each; 2023 has 20; 2024 has 3 available captures.
- Notice date is read from archived HTML. It is deliberately separate from Wayback capture year; a 2024 capture can contain an older notice.
- Event fields retain names directly visible in the source text. The suit column is a source-text candidate list, not a Parser result: bracketed names that are clearly resources, components, or rewards are excluded where identifiable, but ambiguous historical wording is retained for human review.
- `Wayback request failed` means the snapshot was not reachable during this research run; it does not mean an official notice did not exist.

## Player-facing event identity findings

### Fixed series / gameplay are families, not one event

- **Dream Wedding / 夢戀奇迹** is a wedding gameplay brand. Each theme and suit bundle is a concrete event; only the same theme and core suits reopening should add an `event_period`.
- **Wish Court / 願之庭** and limited draw pavilions identify a venue or mechanism. A named draw theme, such as Love and Magic Dream, is the player-recognizable event. Different themes must not merge.
- **Starry Corridor-type long-running modes, museums, fairylands, dawn battles, and guild chapters** are families or systems. A round theme and its suit bundle identify the concrete event.
- **Pavilion, gacha, and draw** describe acquisition mechanics, not identity.

### Same event with periods versus a new event

- Use one event with multiple periods only when the official text preserves the concrete theme, gameplay and core suit set, and explicitly says rerun, return, reopening or equivalent.
- Create a new event for different festival, login, stamina-spend, recharge, channel promotion or collaboration campaigns even when titles share a format. Players perceive different themes, rewards, suits or mechanics as different events.
- Maintenance, opening, defects, probability notices, guild restocks and system explanations are not events.

### Why notice titles are insufficient

- Early notices often use the generic title 新聞公告 while the actual activity name is in the `activity one` body section.
- A seasonal or maintenance notice may contain several activities, login rewards, recharge offers and packs. One notice can map to many events.
- Title changes do not prove identity changes; the same broad gameplay label does not prove identity sameness. Theme plus core suit bundle is stronger evidence.

## Recommended Knowledge DB identity

1. An event should represent a concrete **theme + gameplay + core suit bundle**, never an announcement title, `event.name`, or raw post ID alone.
2. Store an immutable `event_key`; displayed names remain editable attributes.
3. `source_raw_post_id` is provenance, not sufficient identity: one post can contain multiple activity blocks. Link each event through `source_raw_post_id + section/block key`.
4. Reopenings of the same event become `event_period` rows with debut/rerun/return/wish_gate; changed suit bundles strongly indicate a new event.
5. Store fixed gameplay names as `event_family` or category. Do not merge all historical periods of a family into one event.
6. A suit can be reused across periods; `event_suits` must keep the concrete event suit composition and order.

## Conclusion

The player-aligned model is: **concrete campaign = event; same campaign reopening = event_period; long-running gameplay = event_family; one announcement may link to multiple events.**
